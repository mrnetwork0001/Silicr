# Silicr: Threat Model

ZECATHON judges treat leaks as disqualifying. This document lists every party, what it can learn and what it cannot, including the things Silicr does **not** protect. The in-app Leak Inspector shows the same table filled in with live data.

**Pool note.** Since the NU6.3 "Ironwood" upgrade (mainnet 2026-07-28), shielded value paid to Orchard receivers lives in the Ironwood pool. The legacy Orchard pool is withdraw-only, through a turnstile that publishes amounts. Silicr spends Ironwood notes only, so none of its transactions cross the turnstile.

**Network note.** Silicr runs on Zcash testnet or mainnet (small balances, spend caps required on mainnet); the simulated chain exists only inside the test suite (and `pnpm verify`). The public testnet demo is a shared testnet wallet behind `--public-demo` (preset jobs only, no withdraw or policy changes, refused on mainnet). On mainnet, Silicr's transactions sit among every other shielded Ironwood transaction on the network, a far larger crowd than testnet, which weakens the traffic-shape inference in limit #4. Real funds raise the stakes of every limit below, so keep wallets small and read [docs/MAINNET.md](docs/MAINNET.md).

## What each party learns

| Party | Learns | Cannot learn |
|---|---|---|
| **Public chain observer** | That shielded (Ironwood) transactions happened, when, their action counts and their fees. Payments look like ordinary 2-action shielded payments. The padded RFQ (5–8, 9–12 or 17–20 actions) is a less common shape. | Senders, recipients, amounts, memo contents, how many providers were asked (within the padding bucket), and which transactions belong to the same job (shielded transactions aren't linkable on-chain) |
| **Light-wallet server** (lightwalletd; `testnet.zec.rocks` by default) | Each wallet's IP address, every transaction it broadcasts and when, the wallet's birthday height, and any transaction the wallet fetches by txid | Memo contents, amounts, recipients, which notes belong to the wallet (blocks are scanned locally) |
| **Silicr relay operator** | Blob sizes, upload and download timing (one sealed checkpoint per served interval included, so roughly how often intervals end), and the IP addresses of the parties connecting | Blob contents (checkpoints included), which RFQ a blob belongs to, prices, identities |
| **Directory host** | Public provider entries, and the IP of whoever publishes or reads them. Entries are signature-checked by the relay on write and by every client on read, so the host can drop an entry but can't forge or replace one. | Anything about buyers or trades |
| **Providers sent an RFQ (losing bidders)** | The request: GPU type, count, duration; the max price only if the buyer chose `--disclose-max` (by default the RFQ carries 0 = undisclosed, providers bid their own price and the buyer filters bids locally) | The buyer's budget (unless disclosed), who the buyer is, which bid won, the job itself |
| **Winning provider** | The request, the price, the job bundle and its outputs | The buyer's wallet, identity, IP address (both sides only talk to the relay) or other jobs (each RFQ uses a fresh key and address) |
| **Buyer** | Every bid it received, its job and its results | Providers' other jobs or earnings |
| **Silicr arbiter** *(stretch, FROST)* | Bond addresses and the evidence submitted in disputes | Undisputed trades |

## Mitigations we ship
- **Shielded only.** Every address is an Orchard-receiver-only unified address, and the wallet spends Ironwood notes only. Transparent, Sapling and legacy-Orchard (turnstile) spends are refused in TypeScript and again in the Rust wallet, on both the proposal and the finished transaction, with a plain explanation of why.
- **Fixed output buckets** for RFQ transactions, so the action count doesn't show how many providers were asked.
- **Fresh keys per RFQ.** A one-time diversified reply address and a per-RFQ signing key, so one buyer's RFQs can't be linked to each other.
- **Signed protocol messages.** A forged BID or PAY is rejected. Signature checks are strict (RFC 8032).
- **Bounded loss, timed by the buyer's own clock.** The buyer pays each interval shortly before it starts, with random jitter. Heartbeats can block a payment, but they can never trigger one early, so a provider that vanishes or lies about progress takes at most the rest of the interval in progress plus one prepaid interval: at most 1.25 intervals of compute (1.2 on testnet, with 5-minute intervals and a 60-second lead). A buyer that stops paying gets nothing past the interval it paid for: the provider pauses at the unpaid boundary and stops after the grace period. The provider may start an interval on a payment still in the mempool, but that payment must be mined before the next interval starts. So a double-spent payment costs it at most one interval, once. The buyer also keeps the *work product* up to the last paid interval: the provider seals the job's checkpoint dir to the channel key and uploads it at the end of every served interval and whenever it pauses or stops; the buyer verifies the digest and keeps the latest one on disk. If the provider vanishes, `silicr migrate` opens a new RFQ that hands that checkpoint to the next provider inside the sealed job blob. Checkpoints are ciphertext to the relay like every other blob; what the relay gains is one more sealed blob's size and timing per interval, which sharpens limit #4 but reveals nothing else.
- **Proxy-only networking, when configured.** One `proxy` setting routes relay HTTP and the light wallet's gRPC through SOCKS5 with hostname resolution at the proxy; an unreachable proxy stops the daemon rather than leaking.
- **No lookups that reveal interest.** The wallet never asks the light-wallet server for another party's transaction by txid. The Leak Inspector's public view of received transactions is built from blocks the wallet already downloads.
- **Audit without spending authority.** `silicr export-viewing-key` prints the wallet's Orchard-only unified full viewing key (ZIP 316 UFVK) after a loud warning and a go-ahead, and `silicr watch` opens a watch-only wallet from it that lists every payment with amounts, memos and Silicr message types but can never sign a transaction (refused in TypeScript and again in the sidecar). The key is printed once, to stdout, and never logged or sent anywhere. Its holder sees the **whole wallet**: all history, past and future, and which addresses belong together, which is why the warning says to use one wallet per audit scope (docs/ZCASH_SETUP.md §13). Disclosure is the owner's deliberate choice; nothing in Silicr exports a key on its own.

## Known limits (stated, not hidden)
1. **The workload is visible to the winning provider.** Hiding it would need TEE execution with attestation, which is future work. Buyers with secret weights should treat providers as able to see their code and data.
2. **Network metadata.** Without a proxy, the relay sees both parties' IP addresses and the light-wallet server sees each wallet's IP and broadcasts. With `--proxy socks5h://127.0.0.1:9050` (Tor) every outbound connection, DNS included, goes through the proxy and nothing falls back to a direct connection, so they see Tor's address instead (verified against real Tor; see docs/ZCASH_SETUP.md §11). What a proxy does not hide: timing (limit #4), a wallet's birthday height, the fact that a transaction was broadcast at that moment, and Docker image pulls, which the provider's Docker daemon makes from its own IP. A plain `http://` relay is readable by the Tor exit (ciphertext and sizes only); use https or a `.onion` relay.
3. **No proof of correct computation.** Heartbeats show the job is progressing, not that it ran on the claimed GPU or produced honest outputs. Bonds and reputation discourage cheating but don't prevent it.
4. **Timing correlation and the payment train.** The light-wallet server sees the buyer's IP broadcast one padded RFQ, then a run of uniform 2-action payments. From that it can link one job's transactions and infer roughly how long the job ran. Random jitter on payment times blurs the cadence, but not the count. Whoever runs the relay can also line up blob timing with chain timing. Mitigations not yet built: batched payments, randomised upload delays, Tor, and running your own light-wallet server.
5. **Losing bidders see demand.** RFQ details reach every provider asked. Buyers control this by choosing how many to ask.
6. **The arbiter is trusted** in the FROST bond flow (stretch only).
7. **Process-mode runner is not a sandbox.** The Docker runner isolates jobs: no network, read-only filesystem, all capabilities dropped. The process-mode fallback, used when Docker is unavailable, does not, and the provider's status says so.
